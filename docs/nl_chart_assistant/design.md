# 自然言語グラフ生成機能（AIに聞く） 設計書

## 1. 目的

「先月のランチの売上が見たい」「去年と比べて土曜の客数はどう？」のような自然言語の質問から、
適したグラフを自動で選んで表示し、重要な部分を強調して見せる。
さらに「売上が落ちた原因は？」のような質問には、数値の分解結果を文章とグラフのレポートにして返す（12 章）。

## 2. 設計方針

- 判断（どのグラフか・どの引数か）は TypeSafe の Jev、計算と描画はコード、文章生成だけ安価な LLM に任せる
- 既存のグラフ部品を再利用する。Jev には「閉じた選択肢から選ぶ」ことだけをさせる
- UI は独立ページ「AIに聞く」として追加し、既存ページへの影響を小さくする
- 対象は日報・時間別・月別・曜日別・年間・ラーメン・ランチ・アルコールの全ページ

### Jev の特性（設計上の制約）

| 特性 | 設計への反映 |
|---|---|
| 計算・集計・日付比較が苦手 | 期間解釈・集計・強調候補の算出はコードで行う |
| 選択肢が多いと先頭に偏る | 月のような件数の多い集合は Jev に選ばせない。選択肢の順序をシャッフルして一貫性を検証する |
| 文章生成ができない | タイトル・コメントは定型文、または安価な LLM |
| 日本語精度は未保証 | 日本語の質問サンプルで実測してから採用を確定する |
| 入力トークン課金（$0.042/Mtok、出力無料） | 質問は1リクエストにまとめて並列で投げる |

## 3. 処理フロー

図解版のスライドは [flow.md](./flow.md)（Marp）を参照。

```
質問文
 │
 ① コードで前処理: 期間を解釈（「先月」「去年の夏」→ 年月リスト）
 │
 ② Jev（1リクエストで並列に質問）
 │    ・データで答えられるか？ (Noul)
 │    ・どのグラフか？ (Choice: チャートカタログのID)
 │    ・そのグラフの引数 (Choice: 指標/時間帯/モード/曜日…)
 │    ・何を強調したいか？ (Choice: 最大/最小/増減が大きい点/なし)
 │
 ③ 振り分け（上から順に判定。詳細は 7 章）
 │    答えられる確率が低い → 対応外と返す（Jev のみ）
 │    判断に自信がない     → 安価な LLM へ
 │    中程度               → 聞き返す（Jev のみ）
 │    高                   → そのまま実行（Jev のみ）
 │
 ④ コードでデータ取得・集計し、強調候補（最大・最小・変化率）を算出
 │
 ⑤ チャートカタログ経由で描画（強調指定つき）
 │
 ⑥（任意）安価な LLM で一言コメント生成
```

### 3.1 会話の文脈（セッション内のみ）

- DB は持たない。`st.session_state` に「直前のグラフ指定（`chart_id` と引数）」だけを保持する
- 次の質問の Jev の state に `previous_request` として渡し、「じゃあ夜は？」「先月は？」のような省略を補えるようにする
- 画面を更新すると消える（許容する）。会話ログ全文は保持せず、直前の指定のみとすることでトークン量も抑える
- 初期実装では `previous_request` を空にした状態でも動くようにしておき、後から有効化できる作りにする

## 4. 構成

```
src/components/assistant/
├── catalog.py        # チャートカタログ（ID・説明・引数スキーマ・描画関数）
├── dispatcher.py     # カタログから Jev の質問を組み立てて呼び出し、(chart_id, args, confidence) を返す
├── period_parser.py  # 「先月」「去年の夏」などを年月リストに変換（コード）
├── highlight.py      # 強調候補の算出（最大・最小・変化率）
└── fallback.py       # Jev が自信を持てない質問を安価な LLM に回す
src/components/pages/assistant.py  # 独立ページ「AIに聞く」
```

### チャートカタログ

各エントリは以下を持つ。

| 項目 | 内容 |
|---|---|
| `id` | チャートの識別子 |
| `description` | Jev に渡す説明文（意味で書く。引数名ではなく内容を説明する） |
| `args` | 引数ごとの選択肢（閉じた集合）。選択肢ごとに説明文を付ける |
| `render(**args, highlight)` | 描画関数。UI 部品（selectbox 等）を含まない |

### 既存コードのリファクタ

`analytics.py` の各ページ関数は「UI 部品 → データ取得 → チャート」が1つの関数に混ざっている。
データ取得～描画の部分を UI から切り出し、`render_xxx(引数)` として再利用できる形にする。
既存ページも同じ関数を呼ぶ形に寄せ、ロジックの二重管理を避ける。

## 5. チャートカタログ（初期案）

| ID | 元ページ | 引数 |
|---|---|---|
| `daily_bar` | 日報分析 | 月、指標（売上/客数/客単価） |
| `hourly_bar` | 時間別分析 | 月、指標（売上/客数）、曜日 |
| `hourly_compare` | 時間別分析 | 比較する2つの（月・曜日）、指標 |
| `monthly_sum` / `monthly_mean` | 月別分析 | 項目 |
| `weekly_compare` | 曜日別分析 | 比較する2か月、項目 |
| `yearly_bar` | 年間分析 | 指標 |
| `ramen_pie` / `ramen_weekday_bar` | ラーメン | 時間帯、モード、期間 |
| `lunch_pie` | ランチ分析 | 月、モード |
| `alcohol_trend` | アルコール | 種別、モード |

## 6. 強調ロジック

- Jev に「強調箇所そのもの」を生成させない
- コードで候補を算出する（最大値、最小値、前期比の変化が最大の点、外れ値）
- 質問の趣旨（「一番売れた」「落ちた」など）から Jev が強調タイプを Choice で選び、コードがそのタイプで対象を決める
- チャート側に `highlight` 引数（対象のキーと表示スタイル）を追加する

### 強調のスタイル

既存チャートの配色はチャートごとに異なる。

| チャート | 現在の配色 |
|---|---|
| 日報（日次） | 昼 `darkorange` / 夜 `royalblue` の積み上げ、基準線は赤・黒 |
| 月別・年間 | `#46bdc6`（青緑）。最新の1本のみ `#ff6d01`（オレンジ） |
| 時間別 | 曜日ごとに固定色（青・黄緑・金・茶・赤橙）、黒縁 |
| ラーメン・ランチ・アルコール | カテゴリ名のハッシュから色相を生成。「その他」は灰 `#a0a0a0` |

配色がバラバラでも「全体の中で目立つ」ことを保証するため、色ではなく**相対的な見せ方**で強調する。

- 強調対象以外を薄くする（透明度を下げる、または灰色に寄せる）。対象は元の色のまま残す
- 対象に値のラベルを付ける（棒グラフ・折れ線は注釈、円グラフはスライスを少し切り離す）
- 既に配色が1色の月別・年間チャートでは、既存の「最新の1本だけ `#ff6d01`」と同じ表現に揃える
- 強調色は、ハッシュ生成色や既存色と被らないよう `ColorPalette.py` に定数（`HIGHLIGHT_COLOR`）として追加する

## 7. 信頼度の扱い

- 複数の質問がある場合、呼び出し全体の confidence は最も弱い質問に合わせる
- 次のルールを**上から順に**判定する。しきい値は仮置きで、実データで confidence と正答率を測って決める

| 順 | 条件 | 処理 | 担当 |
|---|---|---|---|
| 1 | 「データで答えられる」確率 < 0.2 | 対応外と返す | Jev のみ |
| 2 | 最も弱い confidence < 0.5、または「答えられる」確率が 0.2〜0.5 | LLM に回す | LLM |
| 3 | 最も弱い confidence が 0.5〜0.8 | 聞き返す（Jev の上位候補を選択肢として見せる） | Jev のみ |
| 4 | 最も弱い confidence ≥ 0.8 | そのまま実行 | Jev のみ |

- LLM に回すのは、Jev が判断に自信を持てない場合に限る。「明らかに対応外」は Jev だけで返し、LLM は呼ばない
- LLM の出力（ツール呼び出し）もそのままは実行せず、カタログで検証して、存在しない ID や範囲外の引数は弾く
- 図解は [flow.md](./flow.md) を参照

## 8. セキュリティ・運用

- Jev の API キーはサーバー側で保持する。`.env` または `st.secrets` から読み、コードやリポジトリには置かない
- ユーザーの質問文は外部サービス（TypeSafe）に送られる。売上データ本体は送らず、質問文と選択肢の説明のみを送る

## 9. 検証計画

1. 日本語の質問サンプル（各チャートにつき数件、計 40〜60 件）を作成する
2. Jev でチャート選択と引数の正答率・confidence を測る
3. 選択肢の順序をシャッフルして、結果が変わらないかを確認する
4. 結果をもとに、しきい値とフォールバックの範囲を決める

## 10. 実装順

1. 検証用スクリプトで Jev の日本語精度を測る（上記 9）
2. 2〜3 種類のチャート（日報系 1・メニュー系 1・比較系 1）でカタログ→Jev→描画を通しで動かす
3. 残りのチャートをカタログに追加していく（元ページの UI 切り出しを伴う）
4. 強調表示、聞き返し、LLM フォールバックを追加する
5. 独立ページ「AIに聞く」を `app.py` のナビゲーションに追加する
6. 要因分析レポート（12 章）: 型を1つ作ってレポート生成を通しで動かし、残りの型を追加する

## 11. フォールバック先 LLM

- 役割: Jev が判断に自信を持てない質問の処理（7 章のルール 2。明らかな対応外は Jev だけで返す）
- **第一候補: Claude Haiku 5.5**（`claude-haiku-5-5`）
- 比較対象: Gemini（Flash 系）、GPT-5.6 Luna
- 要件: ツールコーリング（チャートカタログの `id` と引数スキーマをそのままツール定義に変換して渡す）
- フォールバックは全リクエストのごく一部のため、単価の差よりも精度と日本語の扱いを優先して選ぶ
- 選定方法: 検証用の質問サンプルのうち Jev が低 confidence だったものを各モデルに投げて、正答率で決める。第一候補はあくまで実測前の仮置き

### Haiku 5.5 を第一候補とする理由

- ツールコーリングに対応し、`strict: true` で入力がスキーマに必ず一致する。強制のツール呼び出し（`tool_choice` が `any` や名前指定）も受け付ける
- 料金は入力 $0.10 / 出力 $0.50 per 1M トークン（プロンプト 100K トークン以下。2026-10-06 時点）。フォールバックの呼び出し量なら誤差になる
- 日本語の曖昧さ・対応外の判断を含む用途で、第一候補として試す価値がある

### Haiku 5.5 を使うときの注意

- 思考は `thinking` 未指定だとデフォルトで入る。この用途では不要なので `output_config.effort` を `low` にする（代替: `thinking: {"type": "disabled"}`。`low`〜`high` で有効、`xhigh`/`max` では 400。思考を切ると、JSON 出力も求めた場合に必要なツール呼び出しを飛ばすことがある）
- `temperature` は 1 以外を指定すると 400。再現性は、ツールの引数を enum で縛ることで担保する
- 思考が `max_tokens` を消費する。小さすぎる値だと、答えの前に打ち切られる
- レスポンスの先頭が思考ブロックのことがある。`content[0]` ではなく `type` で取り出す
- 拒否（`stop_reason: "refusal"`）にはサーバー側のフォールバック機能がない。`stop_reason` を確認し、拒否は「対応外」として扱う
- 強制のツール呼び出しをすると思考をスキップする（この用途では問題ない）
- LLM 呼び出しは `fallback.py` のインターフェースの内側に閉じ込め、モデルを差し替えられるようにする

## 12. 要因分析レポート（文章＋グラフ）

「先月、売上が落ちた原因は？」のような質問に、数値の分解結果を文章とグラフでまとめて返す。
通常のグラフ表示と同じ振り分け（3・7 章）の上に、「レポート型」をカタログのエントリとして追加する。

### 12.1 処理フロー

```
質問文 → ①〜③は通常と同じ（期間解釈、Jev、振り分け）
 │       Jev が選ぶのは chart_id ではなく report_id（レポート型）と引数
 ④ コードが型の分析を実行（既存の Facade / Utils を呼ぶ）
 │   → 構造化された結果（寄与度の順位、増減額、比較対象など）
 ⑤ コードが「事実リスト」を作る（数値はすべてここで確定）
 ⑥ LLM が事実リストから文章を生成（数値の書き換えは禁止）
 ⑦ コードが文中の数値を事実リストと照合 → 通れば表示、外れれば定型文にフォールバック
 ⑧ 付随するグラフを、強調つきで描画（6 章の仕組みを再利用）
```

### 12.2 レポート型（初期案・未確定）

| ID | 内容 | 分解の軸 |
|---|---|---|
| `sales_change` | 前月比・前年比で売上が増減した要因 | 客数 × 客単価、昼/夜、曜日 |
| `menu_contribution` | メニューカテゴリごとの売上増減への寄与 | カテゴリ別の増減額 |
| `period_summary` | 指定期間の特徴の要約 | 最大・最小、前期比の大きな変化 |

型は分析の実行と結果の形（`analyze(**args)` の戻り値）をそろえて、後から追加できるようにする。

### 12.3 カタログの拡張

| 項目 | chart エントリ | report エントリ |
|---|---|---|
| `id` / `description` / `args` | 共通 | 共通 |
| 実行 | `render(**args, highlight)` | `analyze(**args)` → 構造化結果 |
| 付随物 | なし | `charts`: 結果から付随グラフを作る関数のリスト |
| 文章 | なし | `facts(result)`: 事実リストを作る関数 |

Jev の質問、LLM のツール定義、検証は、chart と report で同じカタログから作る。

### 12.4 文章生成の方針

- 文章を作るのは LLM のみ（Jev は文章を生成できない）。第一候補は 11 章のフォールバックと同じモデルで、ツールコーリングは使わない
- LLM には事実リスト（数値と、その意味を表す短い項目）だけを渡す。売上データそのものや、事実リストにない情報は渡さない
- 数値の算出・単位・丸めはコードで行い、文中の数値は事実リストにあるものだけを許可する
- 照合に失敗した場合は、再生成せず、事実リストから作る定型文で表示する（コストと表示遅延を抑える）
- 「要因」は数値の分解による寄与度の説明にとどめる。天候・イベントなど、データにない外部要因は断定せず、言及しない
- LLM 呼び出しは 1 レポートにつき 1 回。グラフ表示だけの質問では呼ばない

### 12.5 検証

- 事実リストと文中の数値が一致するか（自動チェック）
- 寄与度の合計が、全体の増減額と一致するか（コードの単体テスト）
- 日本語の質問サンプルに、レポート型の質問を追加して、型の選択精度を測る（9 章）
