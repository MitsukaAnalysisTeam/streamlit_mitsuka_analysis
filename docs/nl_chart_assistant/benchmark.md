# ベンチマーク計画（案）

「AIに聞く」で使うモデルを、実際の質問で比較して決めるための計画。
設計の全体は [design.md](./design.md) を参照。

## 1. 目的

次の2つを、同じ質問セットで測って決める。

1. **Jev がどこまで使えるか**（日本語での精度、confidence の信頼性）
2. **Jev が自信のない質問を、どのモデルに回すか**（フォールバック先）

最終的に決めたいのは、モデル単体の優劣ではなく**組み合わせ全体**（Jev → フォールバック）の
正答率・コスト・応答時間。

## 2. 比較対象

| 役割 | 候補 |
|---|---|
| 一次判断 | Jev 1.13（`jev-latest`）、Jev 1.14（`jev-preview`） |
| フォールバック | Gemini（Flash-Lite と Flash の2段階）、GPT-5.6 Luna、Claude Haiku 5.5（`claude-haiku-5-5`） |
| 参考（上限の目安） | Claude Sonnet 5.5（`claude-sonnet-5-5`）。本番では使わず、「どこまで当てられるか」の目安にする |

- 料金は実施時点で各社の公式ページを確認し、結果表に記録する
- フォールバック候補はすべてツールコーリングで同じカタログを渡す
- LLM は temperature 0 で固定する

## 3. 質問セット

### 3.1 構成（目安 100 件）

| 区分 | 件数 | 例 | 期待する動作 |
|---|---|---|---|
| 明確 | 40 | 「先月のランチの売上を円グラフで」 | 正しいチャートと引数 |
| くだけた・省略 | 20 | 「ラーメンどれが売れてる？」 | 正しいチャートと引数 |
| 曖昧 | 10 | 「売上見せて」 | 聞き返し |
| 対応外 | 10 | 「明日の天気は？」「来月の予測は？」 | 対応外と返す |
| 追従（前の指定あり） | 10 | 前: 昼のラーメン → 「じゃあ夜は？」 | `previous_request` を踏まえた指定 |
| 期間表現の揺れ | 10 | 「去年の夏」「ここ3か月」 | 期間パーサの出力が正しい（モデル評価とは別に測る） |

- 全チャート（設計書のカタログ）を最低 3 件ずつ含める
- 質問文は、実際に使う人が書きそうな言い回しに寄せる（たたき台は私が作り、店の人に直してもらう）
- 開発用 30 件と評価用 70 件に分ける。カタログの説明文や質問文のチューニングは**開発用だけ**で行い、評価用は触らない

### 3.2 形式

`benchmarks/nl_chart/dataset.jsonl`（1行1件）

```json
{
  "id": "q001",
  "split": "dev",
  "category": "clear",
  "question": "先月のランチの売上を円グラフで",
  "previous_request": null,
  "expected": {
    "answerable": true,
    "action": "run",
    "chart_id": "lunch_pie",
    "args": {"mode": "売上"},
    "highlight": "none"
  }
}
```

- `action` は `run`（実行）/ `ask_back`（聞き返し）/ `reject`（対応外）のいずれか
- 期間は `args` に含めず、期間パーサの評価として別に持つ

## 4. 各モデルに解かせる問題

どのモデルにも、同じ入力から次を出させる。

- 答えられるか
- チャートの ID
- そのチャートの引数
- 強調タイプ

| モデル | 呼び方 |
|---|---|
| Jev | 質問を1リクエストにまとめる（Noul / Choice を並列）。選択肢の説明文はカタログから生成 |
| LLM | カタログをツール定義として渡し、ツールコーリングで1回呼ぶ。対応外・聞き返しは専用ツールで返させる |

## 5. 指標

### 5.1 精度（自動採点、LLM 採点は使わない）

| 指標 | 内容 |
|---|---|
| チャート正答率 | `chart_id` が一致した割合 |
| 引数正答率 | 引数ごとの一致率 |
| 完全一致率 | チャート・引数・強調がすべて一致した割合 |
| 対応外の拒否率 | 対応外を実行せず拒否できた割合（実行してしまう誤りは重く見る） |
| 聞き返し率 | 曖昧な質問で聞き返せた割合 |
| 追従正答率 | `previous_request` を使う質問の完全一致率 |

### 5.2 安定性

| 指標 | 内容 |
|---|---|
| 再実行の一致 | 同じ質問を3回投げて結果が変わらない割合 |
| 選択肢順序への耐性 | 選択肢をシャッフルして答えが変わらない割合（Jev で特に見る） |
| スキーマ違反率 | 存在しない ID・範囲外の引数を返した割合（LLM） |

### 5.3 Jev の confidence

- confidence の区間ごとの正答率（高いほど当たっているか）
- しきい値ごとの「そのまま実行した割合」と「その中の正答率」

### 5.4 コスト・時間

- 応答時間の中央値と p95
- 1,000 リクエストあたりの費用（実測した入出力トークンから算出）

## 6. 組み合わせの評価（カスケード）

Jev の結果と各 LLM の結果を保存しておき、しきい値を変えながら**後から組み合わせを再計算**する。
追加の API 呼び出しは要らない。

```
各しきい値 t について:
  Jev の confidence ≥ t → Jev の答えを採用
  Jev の confidence < t → LLM X の答えを採用
→ 完全一致率 / フォールバックに回った割合 / 費用 / 応答時間 を計算
```

この表から、「正答率を保てる最もしきい値の高い（LLM に回す割合が少ない）点」と
「LLM を使わない場合との差」を読み取る。

## 7. 採用の判断基準（案）

数値は仮置き。dev の結果を見て評価用に入る前に確定する。

1. 対応外を実行してしまう誤りが少ない（拒否率 ≥ 90%）
2. スキーマ違反率が 1% 未満
3. 完全一致率が、組み合わせ全体で目標以上（目標は dev の結果で決める）
4. 上を満たすなかで、費用が最も低いモデルを選ぶ。満たすモデルがなければ、完全一致率が最も高いものを選ぶ

Jev 単体が基準を満たすなら、フォールバックは「聞き返し」だけにして LLM を外す選択肢も残す。

## 8. 実装

```
benchmarks/nl_chart/
├── dataset.jsonl     # 質問セット
├── adapters/         # Jev / Gemini / GPT / Claude の呼び出し（共通インターフェース）
├── run.py            # モデルを指定して実行し、結果を results/ に JSON で保存
├── evaluate.py       # 指標の計算とカスケードの再計算
└── results/          # 実行結果（コミットしない）
```

- アダプタは `fallback.py` の LLM インターフェースと共通化し、ベンチマークで選んだものがそのまま本番に使えるようにする
- API キーは `.env` から読み、リポジトリには置かない
- 本番コードの `catalog.py` を読み込んで質問と定義を生成する。ベンチマーク専用のカタログは持たない

## 9. 費用の見込み

100 件 × モデル 5〜6 種 × 3 回の実行でも、入力は数十万トークン程度。
各社の単価を考えると、全体で数百円以内に収まる見込み（実施前に各社の料金を確認して見積もる）。

## 10. 進め方

1. 質問セットのたたき台を作り、言い回しを店側で直す
2. カタログを最小限（2〜3 チャート）で作り、Jev で動作確認する
3. 全チャートのカタログができた段階で、全モデルを回す
4. 結果を見て、しきい値とフォールバック先を決める
