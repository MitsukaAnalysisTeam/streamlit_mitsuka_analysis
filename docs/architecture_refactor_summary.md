# システムアーキテクチャ：改修前後まとめ

対象: PR #19（`feature/transaction-data` → `main`）
目的: このPRで何がどう変わったかを、システムに詳しくない人にも分かる形で記録する。図解レポート作成の元資料としても使う想定。

## 1. このアプリについて

「みつか坊主」というラーメン店の売上データを可視化するStreamlitダッシュボード。日報・時間帯別・月別・曜日別・年間の売上/客数指標に加え、ラーメン/ランチ分析/アルコールというメニューカテゴリ別の分析ページがある。

---

## 2. 改修前（`main`ブランチ）の状態

### 2.1 データソース

| ページ群 | データの取得元 |
|---|---|
| 日報/時間別/月別/曜日別/年間分析 | Googleスプレッドシート（複数、日報専用） |
| ラーメン/ランチ分析/アルコール | Googleスプレッドシート「シート1」（`バリエーション別販売数_all`/`バリエーション別売上_all`）**のみ** |

2026年6月にレジ（POS）システムが「バリエーション別（横持ち、商品名が列）」から「会計別（縦持ち、1行=1明細）」に変わったが、改修前の時点では**新形式のデータを取り込む仕組み自体が存在しなかった**。つまり2026年6月以降の売上は、ラーメン/ランチ/アルコール分析に反映されていなかった。

### 2.2 商品名→カテゴリの分類

分類は以下5つの独立したJSONファイルで行っていた。

- `menu.json`：`{カテゴリ名: [商品名, ...]}`という単純な配列
- `lunch.json` / `ディナー.json` / `深夜限定.json`：昼/夜/深夜それぞれ専用の商品名一覧（同じカテゴリでも時間帯ごとに商品名の書き方が違うため、ファイルごと別管理になっていた）
- `alcohol.json`：アルコール専用

これらはいずれも「商品名→カテゴリ」の単純な対応表で、**「このカテゴリはラーメンなのかセットなのかアルコールなのか」という分類情報（flag相当）はコード側にハードコード**されていた。

### 2.3 ハードコードの状態

- どのカテゴリを円グラフに出すか（`TARGET_KEYS`等）
- アルコールをビール/秋鹿/ワインに仕分けるカテゴリ一覧
- カテゴリ名→色の対応表（26件、手書き）
- 「2026年6月は深夜メニューが縮小されていた」という一時的な特例

これらはすべてPythonの`.py`ファイルに直接書かれており、新しいメニューが増えるたびにコード修正が必要だった。

### 2.4 コードの構成

```
src/components/
├── utils/     # 全クラスがフラットに1階層で並ぶ（日報系もメニュー分析系も区別なし）
└── charts/    # 同上
```

### 2.5 既知の問題（改修前の時点で存在していた）

- 新データ（2026年6月以降）を取り込む仕組みが無い
- ハードコードされたカテゴリ一覧の更新漏れにより、実際にグラフからカテゴリが消えるバグが発生していた
- ソースコードの見通しが悪く、日報系のシンプルな処理とメニュー分析系の複雑な処理が同じ場所に混在

## 3. 改修後（このPR）の状態

### 3.1 データソース

| ページ群 | データの取得元 |
|---|---|
| 日報/時間別/月別/曜日別/年間分析 | 変更なし（Googleスプレッドシート） |
| ラーメン/ランチ分析/アルコール | **旧データ**：Googleスプレッドシート「シート1」（2026-06-01より前）<br>**新データ**：別のGoogleスプレッドシート「会計別_全期間まとめ」（2026-06-01以降、新規追加） |

新データも旧データと同じく**Googleスプレッドシート直読み**に統一し、**アプリ起動時に一度だけ取得してキャッシュ**する方式にした（旧データは元々この方式）。これにより、ページを操作するたびに毎回スプレッドシートへ再取得しに行っていた無駄を解消した。

### 3.2 商品名→カテゴリの分類：`menu.json`への一本化

新旧5つのJSONファイル（`menu.json`旧版、`lunch.json`、`ディナー.json`、`深夜限定.json`、`alcohol.json`）を廃止し、**`menu.json`1本に統合**した。スキーマは以下の通り。

```json
{
  "白味噌": {
    "flag": ["1"],
    "item": ["白(ノーマル)", "白味噌ラーメン(ノーマル)", "白味噌(煮卵付き)", "..."]
  },
  "ドラフト": {
    "flag": ["4", "4.1"],
    "item": ["ドラフト(定番L)", "箕面ビール(定番L)", "..."]
  }
}
```

- **`item`**：このカテゴリに属する生の商品名を、新旧のデータソースを問わず全部並べたもの。旧POSの`白(ノーマル)`も新POSの`白味噌ラーメン(ノーマル)`も同じ`item`配列に入っているため、時代をまたいで同じ「白味噌」カテゴリとして1つのグラフに合算される
- **`flag`**：カテゴリの分類コード。`1`=ラーメン、`2`=セット、`3`=その他フード、`4`=アルコール。さらにアルコールのサブ分類として`4.1`=ビール系／`4.2`=秋鹿(日本酒)系／`4.3`=ワイン系を追加した

`menu.json`は店舗側で管理しているGoogleスプレッドシートから、Google Apps Script（GAS）で書き出したもの。**新しいメニューが増えてもコードは変更不要**で、スプレッドシートを更新するだけで正しく分類されるようになった。

### 3.3 新旧データが1つのグラフになるまでの流れ

`src/components/utils/menu_analysis/`配下は`s1`〜`s5`という5つのフォルダに分かれているが、**新旧データが同じ1本の道を順番に通るわけではない**。旧データと新データはそれぞれ別の道を通り、`s4`で初めて合流する（合流後は共通）。

```
【旧データの道】                        【新データの道】
LoaderBefore202606 (s1)               LoaderAfter202606 (s1)
「シート1」を丸ごと取得                  会計別データを丸ごと取得
  │                                      │
  │                                      ▼
  │                              TransactionCategoryMap (s2のツール)
  │                              menu.jsonで商品名→カテゴリに分類
  │                                      │
  │                                      ▼
  │                              TimeSlotClassifier (s2のツール)
  │                              会計時刻から昼/夜/深夜を判定
  │                              （↑分類・時間帯判定とも s3 の
  │                                RamenTransactionUtils等が呼び出す）
  │                                      │
  ▼                                      ▼
lunch.json/diner.json/midnight.json   新データのslot別df_dict
のうち該当slotのものを選ぶ              （s3で完成）
＝分類と時間帯振り分けが1回の操作で
  同時に終わる（s4のFacadeが実行）
  │                                      │
  └──────────────────┬───────────────────┘
                      ▼
         CategoryUnifyMap.normalize() (s2のツール)
         で表記ゆれを最終補正しつつ、
         2026-06-01を境に日付で前後に分割し合体
         ＝「合体」はここ（s4_facades）で完了する
                      │
                      ▼
         s5_formatting
         合体済みのカテゴリ別データを、
         グラフ用の1本のDataFrameに整形
                      │
                      ▼
         charts/menu_analysis/ で描画
```

ポイントは2つ。

- **旧データは`s3`を一切通らない。** 旧POSは昼/夜/深夜で商品名の書き方自体が違っていたため（例:「白味噌」が昼は`白味噌ラーメン(ノーマル)`、夜は`白(ノーマル)`）、`s4`で「どの時間帯用JSON（`lunch.json`/`diner.json`/`midnight.json`）を使うか選ぶ」という1回の操作だけで、分類と時間帯振り分けが同時に終わる
- **新旧データの「合体」は`s5`ではなく`s4`で完了している。** `s5`は合体済みのデータをグラフ用に集約し直すだけの後処理

`s1`〜`s5`という番号は「新旧共通の一本道の順番」ではなく、「関わるファイル・クラスをどのフォルダに置いたか」という整理なので、実際のデータの流れを追うときはこの図（新旧2本の道がs4で合流する形）で見るのが正確。

### 3.4 ハードコードの解消

| 改修前 | 改修後 |
|---|---|
| 円グラフに出すカテゴリ一覧を`.py`に直書き | `menu.json`の`flag`から動的に取得。表示対象は「df_dictに実際に存在するキー」をそのまま使う |
| アルコールのビール/秋鹿/ワイン仕分けを直書き | `menu.json`の`flag`(4.1/4.2/4.3)から動的に取得 |
| カテゴリ名→色の対応表（26件、手書き） | カテゴリ名のハッシュ値から色を自動生成する仕組み（`ColorPalette.py`）に置き換え。新カテゴリが増えても対応不要 |
| 「2026年6月だけ深夜メニュー縮小」の特例コード | 恒久対応ではなかったため削除 |

### 3.5 分類バグの修正

会計別データの「種別１」列は、バリエーション無しの商品では本来空欄のはずが、実際には文字列の`"0"`が入っていた。分類ロジックがこれを空欄と同一視していなかったため、「赤白ブレンド」「溜まり醤油油そば」など多数の商品が誤って「未分類」に落ちていた。

- 修正前：8,889件中2,606件（29%）が未分類
- 修正後：295件（3.3%、残りは別原因の未登録商品）

### 3.6 コードの構成

```
utils/ charts/
├── common/         # 日報系・メニュー分析系の両方が使う共通処理（SpreadSheets, Json）
├── daily_report/   # 日報/時間別/月別/曜日別/年間分析（シンプルな構成）
└── menu_analysis/  # ラーメン/ランチ分析/アルコール（3.3の5段階パイプライン）
    ├── s1_data_sources/
    ├── s2_classification/
    ├── s3_transaction/
    ├── s4_facades/
    └── s5_formatting/
```

処理の複雑さが異なる2つの領域（日報系／メニュー分析系）を分離し、複雑な方だけ処理段階ごとにさらに細分化した。各フォルダに`README.md`を配置。

### 3.7 円グラフの見やすさ改善

- 全体比3%未満の少数カテゴリを「その他」に自動集約（隣接スライスの色の判別しやすさ・凡例の見やすさを改善）。「その他」の中身は凡例・ホバーで確認可能。「その他」は割合の大小に関わらず必ず最後尾に固定表示
- 凡例をクリックするとそのカテゴリの表示/非表示を切り替えられる旨のヒント表示を追加（円グラフ本体と凡例の間の空白スペースに配置）
- 割合(%)表示がグラフ枠からはみ出て途切れる問題に対応し、グラフの描画スペースを拡大

### 3.8 不要ファイルの削除

- `data/raw/daily_report/`のCSV（30ファイル）：日報データが既にスプレッドシート直読みに切り替わっており、実際には参照されていなかったため削除
- 内容が古く実態と乖離していた設計ドキュメント2件（`docs/2026-07-12_chart_plotly_updates.md`、`docs/2026-07-13_codebase_overview.md`）、pytest形式になっていなかった簡易テストスクリプト（`src/tests/test_utils.py`）を削除

## 4. まとめ：改修前後の対比

| 観点 | 改修前 | 改修後 |
|---|---|---|
| 新データ(2026年6月〜)の取り込み | 無し（未反映） | スプレッドシート経由で反映、キャッシュ済み |
| 分類ルールの管理場所 | 5つのJSON＋コードへのハードコード混在 | `menu.json` 1つに統一、コードは動的参照のみ |
| 分類の正確性 | 検証時点で29%が誤って未分類 | 3.3%（既知の未登録分のみ） |
| メニュー追加時の対応 | コード修正が必要な箇所あり | スプレッドシート更新のみで反映 |
| コードの構成 | フラットで日報系/メニュー分析系が混在 | 役割・処理段階ごとに階層化 |
| 円グラフの視認性 | 商品点数増加で色・凡例が煩雑化 | 「その他」集約・凡例操作ヒントで改善 |
